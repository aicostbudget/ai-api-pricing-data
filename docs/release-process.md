## Version decision

`v1.1.0` is the published, trusted dual-projection release. GitHub Pages V1 remains backward compatible; the asset contract and deterministic packaging are additional capabilities. Do not infer the next release version from the `2026-09-30` snapshot date, and do not recycle the historical date tag.

## Projection and asset contract

- **GitHub Pages V1:** canonical repository model records in `api/v1/prices.json` and `api/v1/prices.csv`, with `api/v1/meta.json`. The dated snapshot is the tracked V1 source for a fixed reference.
- **Website Pricing V2:** public Website projection with conditional components and non-token billing. Build its public export using the existing export path; do not substitute the narrower V1 files.
- **Hugging Face Pricing V2:** generated from the same public Website projection. `huggingface/prices.json`, `prices.csv`, `train.csv`, and `meta.json` must pass the Website export check. The HF Viewer may lag and `train.csv` intentionally omits large serialized fields.

For `v1.1.0` and future releases, use projection-qualified asset names. **Must include:** `github-pages-v1-prices.json`, `github-pages-v1-prices.csv`, `github-pages-v1-meta.json`; `pricing-v2-prices.json`, `pricing-v2-prices.csv`, `pricing-v2-meta.json`; `release-manifest.json`; and `SHA256SUMS.txt`. The Website V2 files must byte-match the checked local public export used for HF parity. The V1 files must byte-match the intended tracked snapshot/API output. **Should include:** the HF `train.csv` viewer projection if a consumer needs it, clearly labeled as a reduced view. **Do not include:** the whole generated tree, history files, unpublished preview artifacts, duplicate unqualified `prices.*` names, secrets, or a fabricated DOI. The tag's source archive already contains the tracked snapshot, schemas, methodology, and licenses.

The real candidate manifest is generated by [`scripts/build_release_bundle.py`](../scripts/build_release_bundle.py). Do not keep a pre-commit candidate manifest in `docs/`. It records a candidate status, null release version/date, the exact Dataset and Website commits, snapshot path, schema hash, per-projection counts/timestamps, and for each asset the fixed `source_path`, byte length, media type, and SHA-256. V2 bytes are generated from the pinned Website public projection using the Dataset V2 canonical projection and existing exporter, then byte-compared with the HF mirror at the Dataset commit. V1 bytes come from the pinned Dataset commit's `api/v1/` Git blobs and must match the dated snapshot blobs. This avoids platform-dependent checkout line endings: the old 2026-09-30 Release's V1 `prices.json` used Windows CRLF worktree bytes (SHA-256 `8826ec54...`); the same tag blob with LF is `cdfe8ac2...`. The record content is identical after line-ending conversion, but the byte hashes differ. The manifest is itself included in `SHA256SUMS.txt`; the checksum file does not hash itself.

The builder is offline and refuses an existing output directory. It never modifies canonical data or timestamps. Candidate mode is the default; an eventual final bundle requires both explicit `--release-version` and `--release-date`, which set manifest status to `release` and must be run against the final tag. The default output is `dist/release-candidate/`, excluded by the narrow `.gitignore` rule. Pass both source revisions explicitly; do not use a floating Website ref in a release procedure:

```powershell
$datasetCommit = git rev-parse HEAD
$websiteCommit = git -C D:\ai-cost-control-tool\aicostguard-english rev-parse HEAD
python scripts/build_release_bundle.py --snapshot 2026-09-30 --dataset-ref $datasetCommit --website-repo D:\ai-cost-control-tool\aicostguard-english --website-ref $websiteCommit --output dist/release-candidate
python -m unittest tests.test_release_bundle -v
```

The local candidate is not publishable merely because it builds. Use this manual order for a future release:

1. Freeze the intended Dataset and Website source commits and choose the dated tracked snapshot. Ensure the Dataset working tree/index is clean and the commit equals the intended `origin/main` state.
2. Run the existing Dataset, pricing component, schema, provenance, Pages, and Website/HF local parity validators on those exact source revisions. Do not refresh dates solely to pass a gate.
3. Build the candidate with the pinned commits. Inspect every projection count, schema, timestamp, `source_path`, asset byte length, and hash in `release-manifest.json`.
4. Remove only the ignored candidate directory after recording its file hashes, rebuild with identical arguments, and compare every file byte-for-byte. Verify each `SHA256SUMS.txt` entry against the actual local asset.
5. Only after the source and bundle are accepted, manually create the chosen tag. Rebuild from **that exact tag** into a fresh external temporary directory with `--dataset-ref <tag> --release-version <chosen-version> --release-date <YYYY-MM-DD>`; verify the manifest `git_commit` equals the tag commit. Reject a pre-tag bundle if any source commit changed. Never hand-edit the manifest or checksum file.
6. Manually create the GitHub Release and upload only the eight projection-qualified files from the tag-derived final bundle. Re-download each remote asset and compare SHA-256 with the tag-derived manifest and checksum file.
7. Check the Release body against the manifest's *separate* V1/V2 counts and schemas. Check HF production parity separately; local HF parity does not prove publication.
8. Only after the GitHub release is confirmed, let the repository owner perform any Zenodo integration and verify the resulting DOI before adding it to later metadata.

Release body template (fill from the tag-derived manifest, not memory):

```markdown
Snapshot: YYYY-MM-DD
Dataset commit: FULL_SHA
Website source commit: FULL_SHA

### GitHub Pages V1
Role: backward-compatible Pages API and tracked snapshot
Records: <github_pages_v1.records>
Providers: <github_pages_v1.providers>
Schema: <github_pages_v1.schema and schema hash>

### Pricing V2
Role: Website public pricing export; Hugging Face is its mirror
Records: <pricing_v2.records>
Providers: <pricing_v2.providers>
Export schema: <pricing_v2.export_schema>

Counts may differ by design because the public Pricing V2 projection includes records not present in the narrower V1 API. Download the projection-prefixed assets listed in release-manifest.json; do not combine data and metadata across projections. Include methodology, CC-BY-4.0 data license, MIT code license, and known limitations.
```

## Release gate

All items must pass for the proposed tag commit and asset set:

1. `HEAD == origin/main`; working tree and index clean.
2. Intended snapshot JSON/CSV are tracked by Git at that commit and equal the chosen V1 data assets.
3. Validate workflow passes for the exact commit.
4. GitHub Pages build/deploy workflow passes for the exact commit; verify the public Pages source SHA. Do not start a production server for local HTML checks.
5. Website-to-HF `export_huggingface.py --check` passes against the Website source revision selected for the release.
6. HF production parity is checked separately after HF publication; do not confuse a local export check with live publication.
7. Dataset and model schema validators pass.
8. Pricing component and conditional pricing validators pass.
9. No unexpected generated-data drift, stale verification claims, or manual timestamp refresh.
10. Manifest names the exact tag commit, tracked snapshot, schema hash, and export schema version.
11. Each manifest count reproduces from its named projection; asset metadata counts agree with its own data files. V1 and V2 counts need not agree.
12. `SHA256SUMS.txt` and manifest checksums reproduce from every uploaded asset.
13. `CITATION.cff` validates and cites the published `v1.1.0` version DOI; any future release DOI is backfilled only after its Zenodo record is Published.
14. Release notes state V1/V2 differences and limitations, cite the methodology and both licenses, and match the actual uploaded asset names.

## Citation and DOI sequence

For reproducible research, cite the frozen [`v1.1.0` GitHub Release](https://github.com/aicostbudget/ai-api-pricing-data/releases/tag/v1.1.0), exact Dataset commit `6882e95a8cdf5fb39b75b47bcd9ba0bff63b13d8`, tracked `2026-09-30` snapshot, and [version DOI](https://doi.org/10.5281/zenodo.23087250). This DOI does not identify whatever data is currently on `main`. For current operational use, cite the clean [live dataset URL](https://aicostbudget.com/en/datasets/ai-api-pricing) with an access date and consult the relevant metadata timestamps.
